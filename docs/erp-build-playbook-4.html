Prepare

How to use this guide

You're building the platform described in ERP_SYSTEM_DESIGN.md v1.5.0: a modular Laravel monolith with three layers (tenant user app, tenant admin panel, Super-Admin panel), PostgreSQL row-level security for tenant isolation, a double-entry ledger, Bangladesh VAT and Mushak forms, an offline-first POS, and a small Go program that drives receipt printers and the NBR fiscal device. The latest review (ERP_DESIGN_REVIEW_v1.5.0.md) lists what the design still gets wrong, and each step below tells you which of those items to fix as you build.

The 14 build steps follow the roadmap in design §18. Every step has the same parts: the goal, a gate of decisions to settle first, what to build, copy-ready prompts, how to test it, a "done when" checklist, and how to ship it to GitHub. Tick the checklist boxes as you go; they're saved in this browser only.

The working loop

Use the same six-part loop for every piece of work. The agent writes the code and runs it on the dev server; you approve the plan and each command, read the failing test, and read the review.

  1. PlanAgent reads the design sections and writes a commit-by-commit plan. You approve it.
  2. RedAgent writes the test first and runs it. You see it fail for the right reason.
  3. GreenAgent implements the smallest change and runs the test again.
  4. Full checkPint, PHPStan and the module's tests run on the server, with output pasted back.
  5. ReviewA new conversation, on a different model, reviews the diff against the design.
  6. ShipPull request, CI, human review, squash merge.

How the prompts are written

Each prompt gives the agent four things: where to read (design sections and review IDs), the task, the rules it must keep, and when to stop. Prompts point at files in the repository instead of pasting the design, so the agent always reads the current version. They're written for the Antigravity desktop app, where the agent edits your local clone and runs every command on the dev server over SSH. Start each new conversation with the SSH block, then the prompt. Every activity has a drop-in prompt: setup prompts S0–S5, the step routine R0–R9, utilities U1–U6, and two or three prompts inside each step. The prompt index lists them all. Placeholders look like {N}; replace them before sending.

Keep the agent honest
  • Never accept "done" without the pasted output of the test command.
  • Never let an agent weaken a database rule, delete a test or switch tests to SQLite to make something pass.
  • Read every migration and trigger yourself. The last four design reviews found new SQL defects in each rewrite, and every one of them would have been caught by a test.

2. Why the project uses Request Review

With the app's Default permission preset, terminal commands run in a sandbox that has no network and can't read ~/.ssh, so ssh can't connect. Request Review turns the sandbox off for this project and makes every command wait for your approval, so you read each ssh command before it runs. That matters most for S0, which runs as root on the Proxmox host.

Once Step 2 is merged and the routine is familiar, you can add allow rules for commands you approve all day, in the form command(regex:…). Allowed commands run without asking, outside the sandbox. Never allow anything for kcerp-prox, keep anything that resets data (migrate:fresh, db:wipe, docker compose down -v) out of them, and test each rule before relying on it.

Browser tests on the server need Chromium: run npx playwright install --with-deps chromium there once. It installs system packages, so an administrator runs it.

Two rules for every database test
  • Run against PostgreSQL 17, never SQLite. RLS, triggers, exclusion constraints and NULLS NOT DISTINCT don't exist in SQLite, so a passing SQLite test proves nothing.
  • Connect as app_rw. The POSTGRES_USER in Docker and CI is a superuser, and superusers bypass row-level security.

Running the loop in Antigravity

  1. Plan. Open a new conversation and send the SSH block with R0, then R1 and R2. The agent creates the branch on both sides and writes the plan file; comment on it and approve it before any code is written.
  2. Red. With R3 the agent writes the test locally, commits it, pushes, pulls on the server and runs it there, for example ssh erp-dev 'cd ~/retail-erp && php artisan test --filter=InvoiceImmutability'. Read the failure: it must fail for the reason the test describes.
  3. Green. The agent changes the code, commits, pushes, pulls and runs the test again, then Pint, PHPStan and the module's tests.
  4. Approve with care. Read each command before you approve it. Anything touching database/, Docker volumes or git history deserves a second look; the dev-server rule forbids resets unless you ask.
  5. Look at it.
