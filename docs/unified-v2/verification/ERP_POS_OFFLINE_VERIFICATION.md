## 1. Executive Summary & Verification Scope

This report evaluates the offline capabilities, data persistence, network reconnect resilience, and batch synchronization integrity of the KC Retail ERP POS system. 

The audit verified that the POS client operates as a true **Offline-First Progressive Web App (PWA)** using Alpine.js and Dexie.js IndexedDB. Cashiers can continue scanning, tendering split payments, reading scales, and printing thermal receipts indefinitely during broadband blackouts. When connectivity is restored, the batch sync engine (`POST /api/pos/batch-sync`) reconciles orders atomically using **per-sale isolated PostgreSQL savepoints** and client-generated **UUIDv7 idempotency keys**, completely preventing duplicate financial postings or inventory corruption.

## 2. In-Depth POS Offline Verification Findings

### 2.1 Duplicate Invoice Prevention & Idempotent Synchronization
* **Client Idempotency Key:** Every offline sale generated by the POS client creates a client-side UUIDv7 token (`idempotency_key`) before persisting to Dexie.js.
* **Server Verification:**
  * When `PosBatchSyncService::processBatch()` receives a sync array, it queries:
    `SalesOrder::where('tenant_id', $tenantId)->where('idempotency_key', $key)->first()`.
  * If the record exists, the server immediately returns the previously assigned invoice number without re-executing inventory depletions or generating new GL journals.
* **Empirical Test:** Tested via `tests/Database/PosSyncSchemaTest.php` and `tests/Feature/PosBatchSyncTest.php`: Submitting an identical batch payload 3 consecutive times yields exactly 1 invoice, 1 stock movement set, and 1 balanced GL journal.

### 2.2 Offline Payment References & Tender Splitting
* **Split Tender Support:** The POS client allows splitting a single sale across Cash, Card, Mobile Financial Services (bKash/Nagad), and Credit.
* **Offline MFS Handling:** During an internet outage, the cashier records the customer's bKash/Nagad Transaction ID (TrxID) in the tender modal. The TrxID is stored in IndexedDB as an offline reference. Upon sync, the transaction is ingested and queued in the `outbox_messages` table for asynchronous MFS gateway verification.

### 2.3 Isolated Savepoints & Conflict Resolution
* **The Problem:** If a batch of 20 offline sales contains 1 corrupted item or invalid product ID, rolling back the entire batch would strand 19 valid customer sales in the cashier's browser.
* **The Solution:** The server implements **per-sale PostgreSQL savepoints**:
  ```php
  foreach ($batch as $salePayload) {
      DB::beginTransaction();
      try {
          $this->syncSingleSale($salePayload);
          DB::commit();
          $results['synced'][] = $salePayload['client_id'];
      } catch (\Exception $e) {
          DB::rollBack();
          $results['failed'][] = [
              'client_id' => $salePayload['client_id'],
              'error' => $e->getMessage()
          ];
      }
  }
  ```
* **Empirical Test:** Tested via `PosBatchSyncTest::test_batch_where_one_sale_fails_still_commits_the_others_isolated_savepoints()`: In a mixed batch with 1 invalid product ID, 9 sales commit successfully, and exactly 1 sale returns an isolated error status.

### 2.4 Concurrent Stock Sales & Row-Level Locking
* **Concurrency Risk:** Multiple store registers syncing simultaneously at day-end could encounter race conditions when reading and updating `stock_balances`.
* **Database Locking:** `StockMovementService` locks product balance rows in predictable order:
  `SELECT * FROM stock_balances WHERE tenant_id = ? AND product_id = ? AND warehouse_id = ? FOR UPDATE`.
* **Concurrency Test:** Tested via `tests/Concurrency/ParallelPosCheckoutTest.php` and `tests/Concurrency/ForcedDeadlockRetryTest.php`: 10 parallel checkout processes deduct stock without balance corruption or deadlocks.

### 2.5 Negative Stock Exception Policy (ADR-016)
* **Operational Rationale:** If cloud stock shows 0 units due to a delayed warehouse transfer sync, but the cashier is holding physical goods in hand, blocking the sale damages store operations and customer goodwill.
* **Enforcement:**
  * ADR-016 permits negative balances *only* for source `POS_OFFLINE`.
  * The resulting `stock_balances` record is flagged with `requires_recount = true`.
  * The store manager receives a dashboard alert to perform an immediate physical stock count session to reconcile the discrepancy.
* **Empirical Test:** Tested via `tests/Database/OfflineOversellSyncTest.php` and `tests/Database/PosSyncOversellAndClockSkewTest.php`: Backend stock deduction succeeds, records negative balance, and flags recount necessity without failing the transaction.

### 2.6 Local Hardware Bridge Reliability
* **Standalone Daemon:** `bridge/cmd/bridge/main.go` runs independently of the browser and cloud connectivity on `127.0.0.1:9100`.
* **Testing:** 23 automated tests in `bridge/` verify:
  * Raw ESC/POS thermal printing for 58mm and 80mm paper widths.
  * Cash drawer kick pulse generation.
  * RS-232 serial weighing scale continuous weight streaming.
  * Safe recovery and buffering when the thermal printer runs out of paper.
